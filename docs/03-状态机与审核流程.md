# VisionQC 审核状态机与工作流（Phase 3 实现版）

> 本文描述已落地的 Phase 3 实现；设计取舍、并发测试与代码讲解见 `docs/08-Phase3审核工作流与并发验收.md`。

## 1. 任务状态机

```
[管理员分配]        [质检员开始]          [质检员提交]        [审核员通过]
NEW ─────► ASSIGNED ─────► IN_PROGRESS ─────► SUBMITTED ─────► APPROVED（终态）
                              ▲                    │
                              │                    │ [审核员驳回，原因必填]
                              └──── REJECTED ◄──────┘
                                   （质检员继续修改后重新提交）
```

| 状态 | 含义 | 允许的下一状态 |
|------|------|----------------|
| NEW | 任务已创建，未分配质检员 | ASSIGNED |
| ASSIGNED | 已分配质检员，尚未开始 | IN_PROGRESS |
| IN_PROGRESS | 标注中，可反复保存 | SUBMITTED |
| SUBMITTED | 已提交待审核 | APPROVED、REJECTED |
| REJECTED | 被驳回，等待修改 | IN_PROGRESS |
| APPROVED | 终态，不可撤销 | 无 |

规则集中在 `TaskStatus.canTransitionTo`，Service 每次动作先校验状态机，非法转换返回 409。

## 2. 权限矩阵（后端强制，前端只做按钮隐藏）

| 操作 | 接口 | 允许角色 | 额外校验 |
|------|------|----------|----------|
| 查询任务列表/详情/历史 | GET `/tasks...` | A / I / R | 质检员只能看 `inspectorId=自己` 的任务 |
| 分配质检员 | POST `/tasks/{id}/assign` | ADMIN | 目标用户存在、启用、有 INSPECTOR 角色 |
| 开始/继续修改 | POST `/tasks/{id}/start` | INSPECTOR | 必须是任务归属人；ASSIGNED 或 REJECTED |
| 提交审核 | POST `/tasks/{id}/submit` | INSPECTOR | 归属人；至少 1 个标注框；IN_PROGRESS |
| 保存标注 | PUT `/tasks/{id}/annotations` | INSPECTOR | 归属人；状态为 NEW/ASSIGNED/IN_PROGRESS/REJECTED |
| 读取标注 | GET `/tasks/{id}/annotations` | A / I / R | 质检员仅本人任务 |
| 审核通过 | POST `/tasks/{id}/approve` | REVIEWER | 不能审核自己标注的任务；SUBMITTED |
| 审核驳回 | POST `/tasks/{id}/reject` | REVIEWER | 原因必填；不能自审；SUBMITTED |
| 用户查询 | GET `/users` | ADMIN | 只返回展示字段，不返回密码 |

## 3. 乐观锁与并发

- `inspection_tasks.version` 为 JPA `@Version` 字段，数据库列 `version INT NOT NULL DEFAULT 0`。
- 客户端每次动作必须携带读取时的 `version`；Service 先做显式版本比对（过期 409），再由 JPA 在 flush 时兜底。
- 两个审核员同时审批同一版本：一个成功提交，另一个收到 `OptimisticLockingFailureException`，统一转换为 HTTP 409，事务回滚。
- 审核记录同样带 `version`（V3 迁移 `review_records.version`），保证每条历史能对应到当时的任务版本。

## 4. 事务边界（实现）

| 操作 | 事务 | 说明 |
|------|------|------|
| assign / start / submit / approve / reject | 单个 `@Transactional` | `saveAndFlush(task)` 与 `reviewService.record(...)` 在同一事务；任一失败整体回滚 |
| `ReviewService.record` | `@Transactional(MANDATORY)` | 强制要求已存在事务，从机制上防止状态与历史分事务写入 |
| 图片上传 | 编排式 + `REQUIRES_NEW` 建任务 | 文件先落 staging，DB 成功后再原子移动；失败清理 staging |
| 标注保存 | 单个 `@Transactional` | 全量替换（先删后插），失败回滚保留旧标注 |

`review_records` 字段：`task_id / operator_id / action / from_status / to_status / comment / version / created_at`。

## 5. 指标口径（看板/报表统一定义，Phase 4 实现）

```
不良率(批次) = 该批次 APPROVED 且存在≥1个标注的图片数 / 该批次 APPROVED 图片总数
缺陷图片数 = 存在≥1个标注的已审核通过图片数（多框只计1次）
待审核数量 = 状态为 SUBMITTED 的任务数
每日缺陷趋势 = 按审核通过时间统计的缺陷图片数/日
```
